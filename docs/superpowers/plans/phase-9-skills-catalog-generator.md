## 9.1 Frontmatter scanner and catalog schema

**Why:** The existing skill loader (`packages/opencode/src/skill/index.ts`) already parses frontmatter into `name` and `description`, but it discards `category` and `when_to_use` because the current `Info` schema only has those two fields. We need to extend the schema so the catalog can group and describe skills accurately.

**Files to modify:**

| File | Change |
| :--- | :--- |
| `packages/opencode/src/skill/index.ts` | Extend `Info` schema to include `category` (optional, literal union `process` | `implementation` | `analysis` | `tooling`) and `when_to_use` (optional string). Update `isSkillFrontmatter()` guard and `add()` to capture these fields. |
| `packages/opencode/src/android/catalog-schema.ts` | **Create.** Define `CatalogEntry` (name, description, when_to_use, category) and `SkillsCatalog` (Record<category, CatalogEntry[]>). |
| `packages/opencode/src/android/catalog-generator.ts` | **Create.** Export `generateCatalog(skills: Skill.Info[]): Effect.Effect<SkillsCatalog>`. Group by `category`; skills without category go to `"uncategorized"`. Sort entries alphabetically within each group. |

---

## 9.2 Catalog generator and `init --skills` registration

**Why:** The catalog is a machine-owned artifact generated by `init`. Its **body** must be always-on (the agent reads the whole map every turn). Note: a discovered `SKILL.md` only contributes its name+description to always-on context — its body loads on demand — so the catalog must NOT be a discovered skill. Store it as a standalone doc and inject it explicitly.

**Files to modify:**

| File | Change |
| :--- | :--- |
| `packages/opencode/src/android/catalog-generator.ts` | Implement `writeCatalog(catalog, path)` that serializes the catalog as a compact markdown block (one line per skill) to `.agents/context/skills-catalog.md` (a plain doc, **not** a `SKILL.md` — see 9.3 for explicit injection). |
| `packages/opencode/src/android/generator.ts` | Register `skillsCatalog` generator with ID `"skills-catalog"`. Trigger on full `init` and on `init --skills`. |
| `packages/opencode/src/android/catalog-template.md` | **Create.** Template for the generated catalog markdown. Structure: `## process`, `## implementation`, etc., each with bullet list `- **name**: description | when_to_use`. |

---

## 9.3 Progressive-disclosure loading of full skill bodies on demand

**Why:** The whole point of the catalog is to keep the always-on context small. The agent must load a skill's full body only when it decides to use that skill. The existing `skill` tool already does this; we need to ensure the catalog references are compatible with it.

**Files to modify:**

| File | Change |
| :--- | :--- |
| `packages/opencode/src/tool/skill.ts` | No changes needed to the tool itself, but update `DESCRIPTION` (`skill.txt`) to mention that the catalog lists available skills and that the agent should call the `skill` tool with the exact `name` from the catalog to load the full body. |
| `packages/opencode/src/session/system.ts` | In `SystemPrompt.skills()`, read `.agents/context/skills-catalog.md` (if present) and inject its full body into always-on context as a `<skills_catalog>` block. This is explicit injection — the catalog is NOT routed through skill discovery, so its body is always present (not on-demand). |

---

## 9.4 "Uncategorized" group for external skills

**Why:** Skills from external sources (e.g., Google's official Android skills at goo.gle/android-skills) may not include AndroidCode-specific `category`/`when_to_use` frontmatter. They must still appear in the catalog so the agent knows they exist.

**Files to modify:**

| File | Change |
| :--- | :--- |
| `packages/opencode/src/android/catalog-generator.ts` | In `generateCatalog()`, if a skill lacks `category`, assign it to `"uncategorized"`. If it lacks `when_to_use`, omit that field from the entry rather than emitting an empty string. |
| `packages/opencode/src/android/catalog-template.md` | Include an `## uncategorized` section in the template. |

## Risk

- **Risk:** Catalog becomes stale when skills are added/removed without re-running `init` → **mitigation:** the catalog file header includes a timestamp and a comment: "Regenerate with `init --skills`". In future phases, a file-watcher could auto-trigger regeneration, but that is out of scope here.
- **Risk:** treating the catalog as a discovered skill would only surface its name+description always-on (body on demand), defeating the always-on map → **mitigation (committed approach):** store the catalog at `.agents/context/skills-catalog.md` and inject its body explicitly in `SystemPrompt.skills()`; it is never registered as a discoverable skill, so there is no scan-noise or dot-dir concern.
